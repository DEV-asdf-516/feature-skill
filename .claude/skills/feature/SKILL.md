# feature

피처 하나를 "설계 합의 → 구현 문서 합의 → 구현 → 리뷰 수렴 → 최종 테스트"로 끝까지 처리한다. 오케스트레이터(이 세션)가 하는 일은 **문서 작성과 사용자 질문뿐**이고, 나머지 결정론적 제어는 전부 `scripts/feature-run.sh`(교통정리기)가 맡는다. 러너는 agent 가 아니다 — 판단이 필요한 상태가 나오면 추가 추론 없이 즉시 이 세션으로 반환한다.

사용자가 세션 요약을 요청하면 `<skill_dir>/specs/feature_<번호>/session/SESSION-<YYYY-MM-DD>-<피처>.md`에 작성한다(결정·미해결 쟁점·다음 단계 위주).

## 사전 조건

1. `config.sh`의 역할별 `*_MODEL`·`*_EFFORT`·`TEST_CMD`·`LINT_CMD`가 실제 환경과 일치. 빈 값이나 `CHANGE_ME`가 남으면 가드가 실행 거부.
2. `claude`, `codex`, `jq`, `uuidgen`, `envsubst` 설치·로그인.
3. 저장소 루트에서 실행. `.agent-work/`는 `.gitignore`에 등록돼 있다.

## Phase 0 — 초기화 + 문서 작성 (오케스트레이터)

1. **피처 식별자를 정하고 러너를 `--feature <id>` 로 한 번 실행해 전용 worktree 를 먼저 확정한다.** id 는 영숫자·`._-`(예: `018`, `order-cancel`). 러너가 branch `feature/<id>` 와 worktree `<저장소 옆>/<repo>-feature-<id>` 를 id 로 결정론적으로 정하고, 없으면 원본 working tree 의 현재 상태(미커밋 tracked 변경·untracked 파일 포함, gitignore 파일·`.agent-work` 제외)를 bootstrap 커밋 없이 snapshot tree 로 옮겨 만든다. 원본의 branch/HEAD/index/working tree 는 읽기만 한다. 이후 `request.md`·`design.md`·`implementation.md`·`approach.md`·`feature-scope.json`·`.agent-work`(리뷰·세션·로그)·워커·리뷰어·수정자는 전부 **그 worktree 안에서만** 다룬다. 첫 실행은 `design.md`가 없으므로 `NEED_DOCS(DESIGN_MISSING)`(exit 3)로 즉시 돌아온다 — 정상이며, 로그의 `피처 worktree: <경로>` 줄과 `DESIGN_MISSING` 안내가 절대 경로를 알려 준다. 같은 피처의 계속이면 같은 `--feature <id>` 로 다시 실행하면 기존 worktree 와 그 안의 `.agent-work` 를 그대로 이어서 쓴다(중복 생성 없음, 세션 이어가기가 캐시 절감의 핵심). 같은 worktree 에서 피처를 처음부터 다시 시작할 때만 `--new`를 붙인다(이전 산출물은 `.agent-work/archive/<이름>/`으로 `mv`, rm 금지). 부트스트랩이 거부되는 경우(원본에서 러너가 실행 중, dirty submodule, snapshot 도중 원본 변경)는 exit 1 이며 사유를 사용자에게 보고하고 원인이 해소된 뒤 재실행한다 — 다른 방법으로 우회하지 않는다.

```bash
bash <skill_dir>/scripts/feature-run.sh --feature <id>          # 처음이든 재실행이든 항상 이 형태
bash <skill_dir>/scripts/feature-run.sh --feature <id> --new    # 같은 worktree 에서 피처를 처음부터 다시
```

2. 사용자 요구를 `<worktree>/.agent-work/request.md`에 기록(원문 + 해석한 범위 + 명시적 제외). 스펙 폴더(`<skill_dir>/specs/feature_<번호>/`)에 문서·이미지가 있으면 전부 읽어 반영. **모호하면 추측 대신 사용자에게 질문**하고 `decisions.md`에 `- [USER-QUESTION][scope=design] <질문> → <답>` 형식으로 기록(Phase 0 의 요구·설계 질문은 항상 `scope=design`).
3. `<worktree>/.agent-work/design.md` 초안: 목표, API/데이터 계약, 에러·동시성 처리, 테스트 기준, 비범위. 갈리는 설계 판단은 옵션을 제시해 사용자 결정을 받는다. 아래에서 `.agent-work/…` 는 항상 피처 worktree 안의 경로다.

## Phase 1 — 러너 실행

```bash
bash <skill_dir>/scripts/feature-run.sh --feature <id>
```

러너가 Phase 0 에서 확정한 worktree 로 들어가 `preflight → design → impl → worker → review → verify → done`을 연결한다. worker 는 전체 feature 를 워커 한 번에 맡기지 않고 `implementation-units.json` 의 구현 단위를 순서대로 직렬 실행한다(아래 "구현 단위 직렬 실행") — unit 사이에는 review/verify 가 없고, 모든 unit 이 끝난 뒤 기존 전체 review(`impl-review-loop.sh`) 를 한 번, 이어서 verify(`TEST_CMD` → `LINT_CMD`, 실패하면 워커 수정 → 재리뷰) 를 기존과 같은 의미로 수행한다. 복잡도·중복·dead code 분석은 프로젝트가 `LINT_CMD`에 구성한다 — 스킬은 언어 독립이라 자체 코드 검사를 갖지 않고, 커버리지 % 게이트도 두지 않는다(숫자 채우기 테스트 유발). 실시간 로그 창(`feature-live`)은 러너가 연다 — **오케스트레이터는 `feature-live` 를 직접 실행하지 않는다.** 러너가 `.agent-work/.feature-live.lock/viewer.pid` 의 PID 생존으로 이미 열려 있는지 확인하고 절대 경로로 새 터미널을 연다. 열려 있는지 궁금하면 그 pid 파일만 본다(`kill -0 "$(cat .agent-work/.feature-live.lock/viewer.pid)"`). 사람이 수동으로 열 때만 절대 경로 `"$(git rev-parse --show-toplevel)/feature-live"` 를 쓴다(피처 worktree 에는 `feature-live` 가 gitignore 되지 않은 경우에만 snapshot 으로 복사된다 — 없으면 원본 저장소 루트의 파일을 worktree 로 `cd` 한 뒤 절대 경로로 실행한다). 진행은 피처 worktree 의 `.agent-work/live.log`와 `run-state.json`으로 관찰한다. **종료 코드로만 다음 행동을 정한다:**

| exit | status | reason | 오케스트레이터 행동 |
|---|---|---|---|
| 0 | `DONE` | — | Phase 2 보고 |
| 3 | `NEED_DOCS` | `DESIGN_MISSING` | Phase 0의 2·3 수행 후 재실행 |
| 3 | `NEED_DOCS` | `IMPL_DOCS_MISSING` | 설계 합의 완료. 아래 "구현 문서 작성" 후 재실행. `implementation-units.json` 이 없거나 스키마에 어긋나거나 unit scope 가 전체 범위 밖일 때도 이 reason 이며 `detail` 에 사유가 있다 — 고친 뒤 재실행하면 impl 재합의를 거친다 |
| 2 | `NEED_USER` | `ASK_USER` | 검증자가 문서 재작성으로 풀 수 없다고 판정(허용 범위 밖 공용 컴포넌트 수정 필요, 또는 제품 정책 선택). `state.json.review`의 해당 이슈 `user_question`과 `options`를 **그대로** 사용자에게 전달. 답을 `decisions.md`에 `- [USER-QUESTION][scope=<stage>] <질문> → <답>` 으로 기록(stage 가 design 이면 `scope=design`, impl 이면 `scope=impl`) → 문서 반영 → 재실행 |
| 2 | `NEED_USER` | `DEADLOCK` / `MAX_ROUNDS` | 마지막 리뷰 JSON(`state.json.review`)의 쟁점만 사용자에게 보고하고 멈춘다. 답을 `decisions.md`에 `- [USER-QUESTION][scope=<stage>] <질문> → <답>` 으로 기록(design 단계면 `scope=design`, impl 단계면 `scope=impl` — 러너 detail 에 써야 할 태그가 그대로 있다), 문서 반영이 필요하면 반영 후 재실행. 사용자가 검증자 요구를 기각한 경우도 같은 형식으로 기록만 하면 된다 — impl 의 `scope=impl` 결정은 design PASS 를 깨지 않으므로 impl 만 Round 1 부터 재검증되고, 검증자는 그 결정을 확정 계약으로 보고 같은 요구를 다시 blocker 로 만들지 않는다. `consensus-*.json` 지문 재계산·PASS 리뷰 JSON 수정 같은 수동 복구는 없다 |
| 2 | `NEED_USER` | `UNDECIDED` | 워커(unit 워커·review-gap 워커·verify 의 worker-fix)가 `undecided`를 냄 — `DOC_GAP`(제품 동작은 정해져 있는데 approach.md 에 그 material 결정만 빠짐)이든 `USER_DECISION`(어느 문서에도 없는 제품 정책)이든 **구현 시점에 워커가 정할 권한이 없는 material 선택이므로 둘 다 사용자 판단**이다(kind 는 진단 정보일 뿐, 정책은 같다). 러너는 `doc-gap-resume.json`(WAITING_USER, 발생 시점 source tree·문서 지문·pending gap 목록)을 남기고 멈춘다. 각 항목의 `decision_needed`·`options`·위치를 **그대로** 사용자에게 전달하고, 답을 `- [USER-QUESTION][scope=impl][worker-gap=<unit id>#<n>] <질문> → <답>`(태그는 detail 에 그대로 있다, 빈 답 불가)으로 기록 → 오케스트레이터가 그 결정을 `approach.md` 에 최소한으로 동기화 → 재실행. **검증자·디자이너(child DESIGNER)를 부르지 않는다** — 재실행은 impl 재합의 없이 같은 unit(완료된 앞 unit 은 건너뜀)부터 워커를 다시 돌린다 |
| 2 | `NEED_USER` | `REVIEW_DOC_GAP` | 리뷰어가 `DOC_GAP` issue(UNDECIDED_APPROACH 등)를 냄 — 구현 리뷰 시점에 드러난 미결정 solution shape. 같은 리뷰에 `FIX_CODE` 가 섞여 있어도 수정자를 먼저 돌리지 않고 리뷰 전체를 체크포인트한 뒤 돌아온다. `doc-gap-resume.json` / detail 의 issue id·`user_question`·`options`·basis/code refs·`impact` 를 **그대로** 사용자에게 전달(리뷰어는 우열을 고르지 않는다). 답을 `- [USER-QUESTION][scope=impl][review-issue=<issue id>] <질문> → <답>` 으로 기록 → `approach.md` 최소 동기화 → 재실행. 재실행은 검증자·디자이너·impl 재합의 없이 **review-gap 워커 1회**(`prompts/worker-review-gap.md`: DOC_GAP 은 사용자 결정 그대로 구현 + 같은 리뷰의 FIX_CODE 를 함께 해결, 새 설계 선택 금지, 기존 `run_worker` 의 scope/index/baseline/manifest/write-set 게이트 그대로) → 새 attempt 의 리뷰로 간다. 워커가 또 새 gap 을 내면 다시 `UNDECIDED` 로 돌아온다(자동 루프 없음) |
| 2 | `NEED_USER` | `DOC_GAP_SOURCE_CHANGED` | 사용자 답을 기다리는 동안(또는 review-gap 워커 호출 직전) source worktree 가 DOC_GAP 발생 시점 tree 와 달라짐. 기존 리뷰·워커 결과를 조용히 재사용하지 않고 멈춘다(자동 restore 없음). `.agent-work` 의 decisions/approach 변경은 source 변경이 아니다. 사용자가 ① 그 tree 로 명시적으로 되돌리고 재실행하거나 ② 변경을 유지하려면 `doc-gap-resume.json` 을 치우고 재실행(새 리뷰 필요 — 이때 impl 지문이 stale 이면 impl 재합의를 거친다) |
| 2 | `NEED_USER` | `DECISION_SCOPE_REQUIRED` | `decisions.md`에 scope 없는 옛 형식 `- [USER-QUESTION] …` 줄이 있음(LLM 호출 전 preflight). 러너는 어느 단계의 결정인지 추정하지 않는다 — detail 의 행번호를 보고 사용자와 확인해 `[USER-QUESTION][scope=design]` 또는 `[USER-QUESTION][scope=impl]` 로 고친 뒤 재실행 |
| 2 | `NEED_USER` | `TEST_RETRIES_EXHAUSTED` / `APPROVAL_STALE_REPEATED` | 로그(`reviews/verify-*.log`)와 상황을 정리해 사용자 보고 후 멈춘다 |
| 3 | `NEED_DOCS` | `SCOPE_MISSING` | `feature-scope.json` 이 없다. 아래 "구현 문서 작성" 3번대로 작성 후 재실행 |
| 2 | `NEED_USER` | `FOREIGN_WORKTREE_CHANGE` | 리뷰어가 `OUT_OF_SCOPE_CHANGE` 를 냄. **자동 원복하지 않는다** — 같은 working tree 의 다른 세션 변경일 수 있다. `state.json.review` 의 해당 이슈 파일 목록을 사용자에게 보여 주고, 사용자가 "워커 과잉 변경이라 되돌린다 / 다른 작업이라 보존하고 범위를 넓힌다" 를 결정한다. 파이프라인은 어느 쪽도 스스로 하지 않는다 |
| 2 | `NEED_USER` | `SCOPE_VIOLATION` | 워커·수정자 호출 전후 write-set 이 `feature-scope.json` 범위를 벗어남(`state.json.files`). 위와 같이 사용자 결정. 자동 원복 금지 |
| 2 | `NEED_USER` | `SCOPE_MANIFEST_CHANGED` | `feature-scope.json` 이 워커 진입 시 확정한 `feature-scope.lock.json` 과 다르거나, 워커·수정자 호출 중 둘 중 하나가 바뀜(범위를 넓혀 검사를 우회하는 경로). 자동 복구 없음. 의도한 범위 변경이면 사용자가 lock 을 지우고 재실행(impl 재합의 → 새 lock), 아니면 원본을 lock 과 같게 되돌린다 |
| 2 | `NEED_USER` | `SCOPE_BASELINE_CHANGED` | 워커·수정자 호출 중 `worker-baseline.tree` 가 바뀜. 이 파일은 `new_file_roots` 아래 소유권 판정의 기준이라 바꾸면 기존 파일 보호가 풀린다(빈 tree 로 바꾸는 우회). 러너·루프는 호출 전에 읽은 값으로 판정하고 파일 변경은 자동 복구 없이 중단하며, 기대값을 `worker-baseline.guard.json` 에 남긴다(index·manifest 검사보다 먼저 기록하므로 다른 사유로 먼저 종료해도 가드는 남는다). 복구 전 재실행은 stage 와 무관하게 러너 진입 시 전역 검사에서 모델·테스트 호출 0회로 같은 사유로 다시 멈춘다(변조된 값을 새 기준선으로 읽는 우회, verify 의 worker-fix 중단 뒤 verify 재진입으로 DONE 이 되는 우회 차단). 사용자가 원래 값(`expected`)으로 되돌리고 워커·수정자 변경을 확인한 뒤 재실행 |
| 2 | `NEED_USER` | `UNITS_MANIFEST_CHANGED` | `implementation-units.json` 이 워커 진입 시 확정한 `implementation-units.lock.json` 과 다르거나 unit 워커 호출 중 바뀜. 자동 복구 없음. 의도한 분할 변경이면 사용자가 lock 을 지우고 재실행(impl 재합의 → 새 lock, spec 이 그대로인 unit 의 완료 체크포인트는 유지), 아니면 원본을 lock 과 같게 되돌린다 |
| 2 | `NEED_USER` | `UNIT_SCOPE_VIOLATION` | unit 워커가 전체 범위 안이지만 현재 unit 의 scope 밖 경로를 바꿈(`detail` 에 경로). 원복하지 않고 멈춘다 — 과잉 구현이라 되돌릴지, 분할이 잘못돼 `implementation-units.json` 을 고칠지(impl 재합의) 사용자가 정한다. 다음 unit 으로 가지 않는다 |
| 2 | `NEED_USER` | `UNIT_CHECKPOINT_CHAIN_STALE` | 다시 실행해야 하는 unit N 뒤에 완료 체크포인트가 있는 unit 이 있음(`detail` 에 목록과 N 의 `before.tree`). 뒤 unit 은 옛 N 결과 위에 작성됐고 그 코드가 worktree 에 남아 있으므로 spec_hash 가 그대로여도 재사용하지 않는다. 자동 원복·replay 없음 — 사용자가 worktree 를 N 의 `before.tree` 로 되돌리고 뒤 unit 의 `units/<id>/` 를 치운 뒤 재실행 |
| 2 | `NEED_USER` | `UNIT_TEST_RETRIES_EXHAUSTED` | unit 의 `targeted_test` 가 `MAX_TEST_RETRIES` 회 수정 뒤에도 실패. `units/<id>/targeted-test-NN.log` 를 정리해 사용자 보고 |
| 2 | `NEED_USER` | `DESIGNER_SCOPE_VIOLATION` | 디자이너(편집 역할)가 합의 문서·`decisions.md` 밖의 source 작업 트리를 바꿈(CLI 종료코드와 무관). 검증자는 문서를 검증하는 역할이지 디자이너가 바꾼 구현 코드를 승인하는 역할이 아니므로 검증자로 넘기지 않는다. 자동 원복·같은 디자이너 자동 재호출 없음 — 호출 전 tree 를 `designer-scope.guard.json` 에 남기고, 복구 전 재실행은 모델 호출 0회로 같은 사유로 멈춘다. 사용자가 변경을 확인한 뒤 작업 트리를 그 tree 로 되돌리면 재개된다(문서까지 바뀌어 있었다면 기존 재개 규칙대로 디자이너를 다시 부르지 않고 다음 검증 라운드로) |
| 2 | `NEED_USER` | `WORKER_OUTCOME_UNCERTAIN` | 워커 CLI 가 non-zero 로 끝났고 이번 호출의 결과 JSON 이 없거나 깨졌는데 작업 트리는 바뀜(index·manifest·기준선·write-set 게이트는 모두 통과). 완료 여부를 알 수 없으므로 같은 워커를 자동 재호출하지 않고 변경도 원복하지 않는다 — 호출 전 tree 를 `worker-outcome.guard.json` 에 남기고, 복구 전 재실행은 모델 호출 0회로 같은 사유로 다시 멈춘다. 사용자가 변경을 확인한 뒤 작업 트리를 그 tree 로 명시적으로 되돌리면(`git checkout <tree> -- <경로>` 등, 러너는 하지 않는다) 재실행 시 워커가 다시 돈다. 결과 JSON 이 유효하면(parse·필드·DONE/UNDECIDED 모순 검사) non-zero 여도 이 사유가 아니라 `[WARN] CLI_EXIT_STATUS_MISMATCH` 로 기록하고 재실행 없이 진행한다(디자이너·수정자는 변경이 있으면 각각 다음 검증자·리뷰어에게 넘긴다; `cli-anomalies.jsonl` 에 append, `usage.jsonl` 의 raw exit_code/success 는 그대로) |
| 1 | `ENV_ERROR` | — | 원인 확인 후 재실행. 진행 금지 |

재실행은 항상 같은 명령이다(`--feature <id>`, 수동 `--worktree`/`--branch` 를 썼다면 그 인자도 같이). 러너가 `run-state.json`의 stage 힌트와 실제 산출물(합의 체크포인트 `consensus-design.json`/`consensus-impl.json`의 PASS + 현재 입력 지문 + 참조 리뷰 JSON 내용, `worker-result.json` + `units/<id>/done.json`, `approved.fingerprint`)을 교차 확인해 재개 지점을 스스로 고른다 — 오케스트레이터가 단계를 지정하지 않는다. impl 이상으로 가려면 design PASS 가, worker 이상으로 가려면 impl PASS 가 현재 입력(design: request/design + `[USER-QUESTION][scope=design]` 줄, impl: request/design/implementation/approach/feature-scope/implementation-units + `[scope=design]`·`[scope=impl]` 줄 — downstream 은 upstream 결정을 상속하지만 upstream 은 downstream 결정을 보지 않는다)에 대해 유효해야 하며, 문서를 고치고 재실행하면 해당 합의부터 다시 돈다. **예외는 구현 후 DOC_GAP 해결뿐이다**: `doc-gap-resume.json` 이 pending(WAITING_USER/WORKER_PENDING/REVIEW_PENDING)이면 impl 지문 추론보다 먼저 `doc-gap` 경로로 간다 — 사용자가 답과 approach 동기화를 마치면 러너가 그 시점의 impl 입력 지문을 `resolved_impl_fingerprint` 로 고정하고(기존 validator PASS 는 위조·덮어쓰기하지 않는다, `base_consensus_review` 가 그 PASS 를 가리킨다), 이후 impl PASS 가 stale 이어도 그 지문이 현재 입력과 같으면 impl 로 되돌리지 않는다(`impl_docs_accepted`). 그 뒤 문서를 또 고치면 지문이 달라져 정상적으로 impl 재합의를 거친다. 즉 최초 구현 전 source of truth 는 합의 문서이고, post-DOC_GAP 은 합의 문서 + 해당 gap 의 명시적 사용자 결정 + 동기화된 approach 다. WAITING_USER 동안은 모델을 부르지 않으며, 프로세스가 워커 직전/직후/리뷰 직전에 죽어도 다음 실행은 체크포인트 단계(WORKER_PENDING → 워커, REVIEW_PENDING → 리뷰)부터 잇는다(review-gap 워커 결과의 after tree 가 현재 트리와 같으면 재호출하지 않는다). review 이상으로 가려면 `implementation-units.lock.json` 이 있을 때 모든 unit 의 `done.json` 이 유효해야 한다. 문서 합의 루프는 stage 보다 잘게 `consensus-design.json` / `consensus-impl.json` 에 round 와 다음 단계(`VALIDATOR_PENDING` / `DESIGNER_PENDING` / `PASS`)를 기록한다 — 검증자가 끝난 뒤 디자이너 호출이 실패(모델 ID 오류 등)하면 재실행은 같은 리뷰 JSON 으로 디자이너만 다시 부르고, 디자이너가 문서를 일부 고친 뒤 죽었으면(입력 지문 불일치) 같은 수정을 반복하지 않고 다음 검증 라운드로 간다. PASS 도 입력 지문과 함께 캐시되어 입력이 그대로이고 참조 리뷰가 실제 현재 계약의 PASS 이면 검증자를 다시 부르지 않는다. 지문은 세 종류다: editable(대상 문서 + `decisions.md` 전체 — 스냅샷·diff·변경 파일 목록과 같은 집합, 디자이너 부분 실행 감지), upstream(design 은 `request.md`, impl 은 `request.md`+`design.md`, + `[USER-QUESTION]` — 바뀌면 저장된 리뷰가 무효라 Round 1 부터), PASS(입력 문서 전체 + `[USER-QUESTION]` — 이후 판정 기록이 쌓여도 PASS 가 무효화되지 않음). 체크포인트 포맷은 `config.sh`의 `CONSENSUS_CHECKPOINT_VERSION`/`REVIEW_CHECKPOINT_VERSION`으로 따로 버전을 매기며, 지문 의미가 바뀌면 올린다 — 다른 버전의 체크포인트는 지문을 비교하지 않고 처음(Round 1 / 새 attempt)으로 돌아간다. `ASK_USER`/`DEADLOCK`/`MAX_ROUNDS` 로 멈추면 체크포인트는 Round 1 로 초기화된다(사용자 수정 후 처음부터 재검증). 구현 리뷰 루프도 같은 구조로 `review-impl.json` 에 attempt·round·다음 단계(`REVIEWER_PENDING` / `FIXER_PENDING` / `APPROVE`)와 작업 트리 지문을 기록한다 — 리뷰어가 `REQUEST_CHANGES` 를 낸 뒤 수정자 호출이 실패하면 재실행은 같은 attempt 에서 기존 리뷰 JSON 으로 수정자만 다시 부르고, 수정자가 코드나 `decisions.md`를 일부 고친 뒤 죽었으면(작업 트리 + `decisions.md` 지문 불일치) 다음 리뷰 라운드로 간다. 수정자가 완료된 뒤(`REVIEWER_PENDING`) 외부 변경이 들어왔으면 종결 검토에 섞이지 않도록 새 attempt 의 Round 1 로 간다. `APPROVE` 는 작업 트리만의 지문이 그대로이고 참조 리뷰가 실제 현재 계약의 APPROVE 이면 재사용하고, 바뀌었으면 새 attempt 를 시작한다. 러너도 verify 로 바로 들어가기 전에 같은 조건(`impl_approval_current`: 체크포인트 APPROVE + 계약·포맷 버전 + 트리 지문 + `approved.fingerprint` 일치 + 실제 APPROVE 리뷰)을 확인하고, 아니면 review 부터 다시 간다. `DEADLOCK`/`MAX_ROUNDS`/`DOC_GAP` 종료 시 체크포인트는 초기화되어 다음 재진입은 새 attempt 의 Round 1 이다(리뷰어 DOC_GAP 은 `doc-gap-resume.json` 에 리뷰 경로·attempt/round·source tree 를 따로 남긴다).

### 구현 문서 작성 (`IMPL_DOCS_MISSING` 반환 시)

합의된 `design.md` 기반으로 네 파일을 쓴다. 설계 합의를 재해석·번복하지 않는다.

1. `.agent-work/implementation.md` — **무엇을** 구현하는가(도메인 지식)를 **material implementation contract** 수준으로 확정한다. 계획서가 아니지만 코드 blueprint 도 아니다 — 워커가 제품·아키텍처·책임 경계·재사용 관계·비용 특성을 새로 선택하지 않을 만큼만 구체화한다. 구현 대상마다 필요한 것만 확정한다: 변경·생성 대상 / material public·package symbol 과 signature / 입력·출력 계약 / 책임 경계(누가 판단·조립하는가) / 외부 상태 변경 / 중요한 호출 관계 / 중요한 상태 변경 순서 / 테스트할 observable behavior / 테스트 계약. 자동으로 쓰지 않는 것: private helper 이름·개수, local 변수 이름, local collection 배치, for/stream, 동일 overload 중 하나, 의미 차이 없는 intermediate result type, production pseudocode(material control-flow 가 복잡해 오해를 막을 때만). 형식 예:
   ```
   File: <path>
   Function: A.process(input) -> Result
   변경: 기존 X 조회 유지 · Y.build(...) 호출 추가 · 반환된 Z 를 P.publish(...) 에 전달 · 기존 inline 변환 로직 제거
   호출 순서: 1. X 획득 → 2. Y 호출 → 3. 실패 결과면 즉시 반환 → 4. 성공 결과를 P 에 전달 → 5. 결과 반환
   ```
3. `.agent-work/feature-scope.json` — 이번 피처가 변경·생성하는 **정확한 경로 목록**. `implementation.md` 의 파일 목록을 기계가 읽는 형태로 옮긴 것이며 자연어 목록을 러너가 해석하지 않는다. `files` 의 경로는 생성·수정·삭제가 모두 허용된다. 정확한 파일명을 미리 정할 수 없는 생성 경로(마이그레이션 등)만 `new_file_roots` 에 디렉터리 접두로 최소한만 두며, **그 아래는 워커 진입 기준선(`worker-baseline.tree`)에 없던 경로의 생성·수정(A/M)만 허용**된다 — 이 피처가 만든 파일은 이후 라운드의 수정자·worker-fix 가 다시 고칠 수 있지만 삭제·유형 변경(D/T)은 위반이고, 기준선에 있던 파일의 수정·삭제도 `SCOPE_VIOLATION` 이다(소유 분류는 호출별 A/M 이 아니라 기준선 존재 여부). 기준선 tree 는 호출 전에 읽어 사후 판정에 넘기며 호출 중 파일이 바뀌면 `SCOPE_BASELINE_CHANGED` 로 중단한다. 경로는 canonical 이어야 한다(선행 `./`·후행 `/`·`..` 금지). 러너는 워커 진입 시 이 파일을 `feature-scope.lock.json` 으로 확정하고, 이후 모든 검사·diff·지문은 lock 을 쓴다 — 워커·수정자가 manifest 를 고쳐 범위를 넓히면 `SCOPE_MANIFEST_CHANGED` 로 중단한다. 범위를 바꾸려면 원본을 고치고 lock 을 지운 뒤 재실행한다(impl PASS 지문에 manifest 가 포함돼 재합의를 거친다).
   ```json
   {"version": 1, "files": ["src/main/java/com/example/quote/QuoteService.java", "src/test/java/com/example/quote/QuoteServiceTest.java"], "new_file_roots": ["src/main/resources/db/migration/"]}
   ```
   러너는 이 범위로 (1) 워커·수정자 호출 전후 write-set 을 대조해 범위 밖 변경이 있으면 원복 없이 `SCOPE_VIOLATION` 으로 중단하고, (2) 리뷰 diff 를 범위 경로로 한정하며, (3) 승인 지문을 범위 파일로 계산한다(다른 세션이 범위 밖 파일을 바꿔도 승인·verify 가 무효화되지 않음). 사용자 결정(DOC_GAP 해결)으로 파일 목록이 바뀌어야 하면 원본을 고치고 lock 을 지운 뒤 재실행한다(impl 재합의).
2. `.agent-work/approach.md` — **어떻게** 구현하는가. 단위는 함수가 아니라 **구현 결정**이며, 결정마다 `REQUIRED` 또는 `DELEGATED`를 표시한다.
   - **완성도 기준 = material contract 의 충분성.** 합의는 워커의 모든 판단을 제거하기 위한 것이 아니라, 워커가 소유하면 안 되는 제품·아키텍처·solution-shape 판단만 선점하기 위한 것이다. 판정 문장: 두 구현이 request/design/conventions 를 모두 만족하고 외부 동작·책임 배치·재사용 경로·상태 의미·안전성·의미 있는 비용 특성이 동일하다면, 서로 다른 production diff 가 나온다는 사실만으로 문서 공백이 아니다. **material decision**(사전 합의 대상) = 사용자에게 관찰되는 동작·API 계약 / public·package-level 계약·프레임워크 진입점 계약 / 영속 데이터 모델·정합성 / transaction boundary / concurrency·locking / 보안·권한·개인정보 경계 / layer·module·domain 의 responsibility placement / 기존 공용 책임의 REUSE·EXTEND vs 새 병렬 책임 / sync·async·background 실행 의미 / retry·fallback·cache·error semantics / DB·network·외부 API 호출 topology·횟수 / 실제 요구 규모에서 의미 있게 다른 시간·공간 비용 / 되돌리기 어려운 새 production abstraction·type·state representation / 사용자·명시적 convention 이 직접 요구한 방식. **local implementation expression**(워커 소유) = local 변수 이름 / intermediate local vs inline / 같은 클래스 안의 private helper 추출 vs inline 과 그 signature / if vs switch / 단순 for vs stream / 동일 의미의 SDK·API overload / builder 표현 / 외부 상태·I/O·복잡도에 영향 없는 collection 생성 위치 / 작은 bounded in-memory collection 의 동등한 algorithm 표현 / 반환 직전 local 유무 / 포맷·import·line break / 같은 책임 안의 사소한 private control-flow(명시적 project convention 이 정한 것은 convention 우선). 역할 경계: 오케스트레이터가 material decision 을 결정하고, 워커는 그 안에서 저장소 관례에 맞는 가장 단순한 local 표현을 고르며, 리뷰어는 material 계약·convention·새 standalone abstraction 을 잡는다.
   - **REQUIRED — material decision 또는 사용자·convention 이 명시적으로 고정한 구현 계약만.** 예: "기존 NotificationRepository 를 EXTEND 한다 — 별도 repository 를 만들지 않는다", "외부 API 조회는 batch 1회다", "Redis lock 을 사용한다", "transaction 안에서 상태 A → B 순으로 변경한다", "실패는 retry 하지 않고 FAILED 로 기록한다". 항상 REQUIRED: 외부 관찰 동작·영속 데이터 정합성·보안/권한/개인정보 경계가 갈리는 선택, 사용자가 명시한 방식·기존 코드 재사용. 동등한 local expression 을 diff 동일성 목적으로 REQUIRED 로 선결정하지 않는다 — 그런 문장은 리뷰어가 material 계약으로 취급하지 않는다. pseudocode 는 material control-flow 가 복잡해 오해를 막는 데 실제 필요할 때만 쓰고, 많을수록 완성도가 높은 것으로 취급하지 않는다:
     ```
     ## 결정 3: `A.process` 결과 조립 [REQUIRED]
     result = 새 collection
     primary = componentA.process(input)
     if primary 존재: result.add(primary)
     for each item in additions: result.add(componentB.added(context, item))
     for each item in removals: result.add(componentB.removed(context, item))
     return result
     ```
     여기까지 내려가는 것이 허용된다. 근거는 줄 범위 인용(`path:L40-L68`) 또는 표준 기법 + 선택 이유다.
   - **DELEGATED — material contract 를 지키는 범위의 local implementation expression.** private helper 추출 여부, local 이름, local intermediate 유무, if/switch, for/stream, 동등 overload, 작은 local collection 표현. "아무렇게나" 가 아니다 — 워커는 명시적 project convention → 이미 선택된 material contract → 직접 범위의 명백한 기존 표현 → 언어·플랫폼 관용 표현 → 가장 단순한 직접 구현 순으로 정하며, 새 abstraction 을 만들어 자유도를 소비하는 것은 DELEGATED 의 기본 권한이 아니다. DELEGATED 결정에는 기법을 적지 않으며, 워커는 결과 JSON 의 `delegated_choices` 에 material contract 에 가까워 리뷰어가 확인할 가치가 있는 선택만 보고한다. 리뷰어는 그 목록을 참고만 하고 코드 위치로 판정한다.
   - **단순성 의무.** 문서가 새 production structure(type·record·enum·context·result·helper layer·interface)를 직접 요구하려 할 때는 먼저 묻는다 — 이 구조가 요구사항·책임 경계·상태 모델 때문에 필요한가, 아니면 워커 선택을 제거하기 위해 만든 구조인가? 후자라면 만들지 않는다. `SendOutcome`/`Kind`/`ResultContext`/`private resultOf(...)` 같은 것을 branch 결과를 사전에 타입으로 고정하려고 발명하지 않는다 — 직접 값·기존 타입·local 변수로 충분하면 더 직접적인 쪽을 택한다.
   - **REQUIRED 의 선택 품질.** material 접근법을 REQUIRED 로 확정할 때는 요구와 기존 계약을 만족하는 후보 중 **가장 단순한 통상 해법**을 고른다. 우선순위: 직접 범위의 명백한 precedent → 언어·플랫폼·표준 라이브러리의 표준 기능 → 직접적인 최소 구현. 새 추상화·새 의존성·별도 상태 구조는 앞선 방법보다 요구·기존 계약·필요한 비용 특성을 더 직접적이고 단순하게 만족한다는 구체적 이유가 있을 때만 고르고 그 이유를 적는다.
   - **재사용 탐색(REUSE / EXTEND / NEW).** **새 responsibility boundary** 를 만드는 결정 — 같은 책임의 repository/service/helper 신설, 기존 공용 converter·query path 와 경쟁하는 새 경로, 공유 abstraction/interface, infrastructure component, 새 cross-domain/shared responsibility — 는 같은 모듈·직접 의존 코드에서 같은 책임의 기존 구현을 먼저 찾고 `REUSE`(기존 symbol 호출) / `EXTEND`(기존 symbol 에 메서드·분기 추가) / `NEW` 중 하나를 명시한다. `NEW` 에는 ① 확인한 기존 symbol/path ② 가장 가까운 기존 후보 ③ REUSE/EXTEND 가 요구를 만족하지 못하는 이유가 있어야 하며, 없는 NEW 는 검증자가 `REUSE_DISCOVERY_GAP` 으로 막는다(어느 구현이 나은지는 정하지 않는다). 요구에서 거의 자명하게 파생되는 feature-local 구조 — 새 DB table 에 대응하는 entity/row model, 새 API 계약에 대응하는 DTO/command, design 이 존재를 확정한 feature-local value carrier, 기존 책임과 경쟁하지 않는 단순 feature-local model — 와 같은 클래스 안의 단순 private helper 는 이 근거의 대상이 아니다. 워커는 REUSE/EXTEND 로 정해진 symbol 옆에 병렬 구현을 만들지 못하고(리뷰어 `CONTRACT_VIOLATION`), 명시적 NEW 가 없는 새 standalone 구조물은 `DOC_GAP` 으로 돌려보낸다.
   - **금지 문구.** 금지는 기본적으로 쓰지 않는다. 특정 대안이 요구 불변식이나 선택한 접근법을 깨뜨릴 때만 적고, 그때는 금지 이유와 지켜야 할 불변식 또는 허용 대안을 함께 적는다. 수단 이름만 단독으로 금지하지 않는다(잘못된 형태: "정규식 한 줄 치환 금지". 바람직한 형태: "토큰별 반복 치환은 순회를 n 번 하므로 쓰지 않는다 — 한 번의 왼쪽→오른쪽 스캔을 유지한다").
   - **탐색 범위와 근거.** 기본 범위는 변경 파일 · 같은 모듈 · 직접 의존 코드 · 동일 책임의 인접 symbol · 기존 reference 가 가리키는 코드이며, 무제한 repo-wide 탐색이 아니다. 그 범위에서 기존 utility, 책임 배치, 재사용 경로, 상태 처리 invariant, 같은 유형의 호출부를 확인해 두 문서에 반영한다. 저장소는 **오케스트레이터가 material contract 를 작성하기 위한 근거**다.
   - **reference code.** 따라야 할 precedent 는 반드시 백틱 **줄 범위**로 인용한다(`src/foo/Bar.kt:L40-L68`). 러너가 그 범위만 워커 프롬프트에 `[REFERENCE CODE]`로 직접 붙인다(참조당 100줄·8개 캡). 심볼명이나 범위 없는 경로는 붙지 않으며 검증자가 blocking 으로 돌려보낸다. reference 가 고정하는 것은 책임 배치·재사용 symbol·material control-flow·상태 처리 invariant·project-specific API idiom 중 의미 있는 부분이다. incidental expression(local 이름·helper 개수·줄 구조·같은 의미의 overload·private extraction 여부)은 자동으로 contract 가 되지 않는다 — 정확히 복제해야 하는 이유가 user decision·project convention·material contract 에 있으면 approach 가 그 이유를 명시한다.
   - **제어 흐름 절(선택)** — 외부 동작이나 상태 변경 결과가 갈리는 함수에 "허용된 결정점을 열거하고 그 외 동작 분기를 금지"하는 계약을 쓴다. 모든 함수에 쓰지 않는다. 절이 있는 함수는 REQUIRED 계약이고, 절이 없는 함수라도 호출 순서·branch 조건·aggregation 위치는 위 REQUIRED 규칙대로 결정에 적혀 있어야 한다(워커는 문서에 없는 외부 동작·상태 결과를 새로 정하지 못하고, 리뷰어는 그런 추가를 `UNDECLARED_BEHAVIOR` issue 로 잡는다). 계약 대상은 구문상의 조건문이 아니라 **동작을 달리하는 결정점**이다(루프 종료·관용적 빈값 확인·API 예외 변환·값 계산 boolean·exhaustive match 는 열거하지 않는다). 소스에 분기 ID 주석을 요구하지 않고, 리뷰어는 정상 대응하는 분기를 출력하지 않는다 — 계약 밖 결정점·중복 분기·누락된 분기만 issue 다. 워커는 열거된 결정점만 구현하고 추가가 필요하면 UNDECIDED 로 돌려보낸다. 주 경로는 호출 순서 사양이다 — 문서가 `A → B → C` 로 정했으면 `A → C → B` 는 동작이 같아도 위반이다. 형식:
     ```
     ## `OrderService.process` 제어 흐름 [REQUIRED]
     요구되는 분기:
     - B1 / REQ-03: 주문이 없으면 NOT_FOUND 반환
     - B2 / REQ-04: 이미 처리된 주문이면 현재 결과 반환
     주 경로: 주문 조회 → 처리 실행 → 결과 저장 → 반환
     금지: 위 목록에 없는 null 방어 분기 · 호환성 fallback · 재시도 · 타입별 if 분기 · boolean flag 흐름 제어
     참조 구현: `src/order/ExistingOrderService.java:L40-L68`
     ```
   - 제어 흐름 절은 request.md·design.md에 **이미 명시된** 동작을 옮기는 것이다. 모든 분기를 선제 예측하지 않는다 — 구현 중 실제 공백은 워커가 `DOC_GAP`으로 돌려보내고 사용자가 결정한 뒤 오케스트레이터가 approach.md 에 동기화한다(검증자 재합의 없음). 검증자는 명시된 요구 동작이 빠졌는지만 본다.
   - **완성도는 상세함의 양이 아니다.** 필요 없는 정보를 쓰지 않는다. 최적화 목표는 문서 길이의 최소화도 최대화도 아니라 **material contract 의 충분성**이며, 사소한 helper/local/collection 선택 때문에 DOC_GAP → 사용자 질문이 생기지 않는 것이다. 판정 예시는 `tests/solution-shape-cases.md`.
4. `.agent-work/implementation-units.json` — 위 두 문서가 확정된 **뒤에** 그 구현 범위를 워커가 소화할 수 있는 **기능 단위(implementation unit)** 로 자른 실행 계획(`schemas/implementation-units.schema.json`). impl 합의의 입력이라 impl PASS 지문에 포함되며, 바꾸면 impl 재합의를 거친다. unit 은 새 설계 판단이 아니다 — design/implementation/approach 가 계속 source of truth 이고 unit 은 "이번 워커 호출이 그중 어느 계약을 구현하는가"만 정한다.
   ```json
   {"version": 1, "units": [
     {"id": "01-intake-assignment", "title": "접수 및 담당자 지정", "goal": "문의 접수와 최초 담당자 지정 흐름을 구현한다.",
      "requirements": ["REQ-01", "REQ-02"],
      "scope": {"files": ["src/main/.../InquiryService.java"], "new_file_roots": ["src/test/.../inquiry/"]},
      "references": ["implementation.md#접수-및-담당자-지정", "approach.md#접수-및-담당자-지정"],
      "targeted_test": "./gradlew test --tests '*InquiryAssignment*'"}
   ]}
   ```
   - **분할 규칙.** unit 은 하나의 완결된 사용자/도메인 동작 또는 강하게 결합된 동작 묶음이다(접수+담당자 지정 / Drop 요청+상태 조회 / Drop 승인·반려·취소 …). Repository → Service → Controller 같은 레이어·파일·클래스 종류 기준 분할은 금지. 한 unit 이 끝나면 그 동작의 targeted test 가 가능해야 하고, 뒤 unit 은 앞 unit 이 만든 실제 코드를 쓸 수 있으며, 같은 파일을 여러 unit 이 순차 수정해도 된다. Jira subtask 와 1:1 로 강제하지 않는다. 한 워커가 여러 독립 기능을 동시에 구현해야 하면 너무 큰 것이고, 메서드·파일 하나 수준이면 너무 작다. 모든 unit 의 합집합은 implementation.md 의 구현 범위를 빠짐없이 덮고 unit 간 중복 구현이 없어야 한다. 순서는 선행 동작이 먼저 오도록 정한다(배열 순서 = 실행 순서). 3~8개가 흔한 크기지만 한도는 아니다.
   - **스키마·러너 검사.** `version` 1, `units` ≥1, unit 마다 `id`(순번 prefix + kebab, manifest 전체에서 유일, 순번이 배열 순서대로 증가)·`title`·`goal`·`requirements`(≥1)·`scope`·`references`(≥1)·`targeted_test`(빈 문자열 금지) 필수, 그 외 필드 금지 — `depends_on`·`priority`·parallel 류는 존재하지 않는다(병렬화·DAG 를 만들지 않는다). `scope` 는 `feature-scope.json` 과 같은 `files`/`new_file_roots` 의미(canonical 경로, 둘 중 하나 이상)이며 **전체 범위의 부분집합**이어야 한다 — 러너가 워커 진입 시 lock 대비 검사하고 벗어나면 `IMPL_DOCS_MISSING` 으로 돌려보낸다. 검증자는 ① 전체 범위를 빠짐없이 덮는가 ② 기능 단위인가 ③ 과대·과소 unit 이 없는가 ④ 순서가 선행 관계에 맞는가 ⑤ scope 가 전체 범위 안인가 ⑥ targeted_test 가 그 unit 을 검증하는가 ⑦ 문서에 없는 새 설계 결정이 없는가 만 보고, 더 좋은 분할을 제안하지 않는다.
   - **references 의 정밀도.** unit 은 material decision 을 새로 정하는 곳이 아니다. 각 unit 의 `references` 는 그 unit 이 구현해야 하는 implementation.md/approach.md 의 **정확한 영역**(절 anchor)을 가리켜, unit 워커가 긴 문서 전체에서 자기 구현법을 추론하지 않게 한다. unit 을 더 잘게 쪼개는 것으로 문서 부족을 해결하지 않는다 — 문서 공백은 문서에서 메운다.

### 구현 단위 직렬 실행 (worker stage)

큰 feature 를 워커 한 번에 맡기면 후반부로 갈수록 conventions 가 soft constraint 처럼 밀려 기존 utility/predicate 재구현, `a == X || a == Y` 나열, 불필요한 분기, 책임 배치 이탈이 누적된다. 작은 기능 범위에서는 워커가 기존 컨벤션을 잘 따르므로, 설계 일관성은 전체 문서 합의로 유지하고 **실제 코드 작성만 unit 크기로 제한**한다. 워커 모델을 바꾸는 것도, 리뷰 구조를 바꾸는 것도 아니다 — 바뀐 것은 기존 `run_worker worker-implement.md` 1회가 unit 별 fresh 워커 여러 회가 된 것뿐이고, 그 앞뒤(design/impl 합의, 전체 review/fixer, 전체 verify)의 의미는 그대로다. unit 별 design·review·fixer 는 두지 않는다(변수를 하나만 바꿔 효과를 보기 위해서다. 작은 unit 인데도 컨벤션이 무너지면 그때 별도로 결정한다).

- **직렬만.** 러너는 `implementation-units.json` 을 워커 진입 시 `implementation-units.lock.json` 으로 확정(`feature-scope.lock.json` 과 같은 철학 — 원본≠lock 이면 `UNITS_MANIFEST_CHANGED`, 호출 중 바뀌어도 같은 사유)하고 배열 순서대로 하나씩 돈다. Unit N 이 끝나기(워커 DONE + targeted test 통과) 전에 N+1 을 시작하지 않는다. 병렬 워커·DAG·우선순위·worker pool·투기 실행은 없고 앞으로도 그 추상화를 두지 않는다. 러너는 unit 을 건너뛸지 판단하지 않는다 — 완료 체크포인트가 유효한가만 본다.
- **unit 하나의 흐름.** `units/<id>/` 를 만들고 시작 tree(`before.tree`)를 기록 → **fresh 워커**(`prompts/worker-unit.md`, 세션 `worker-unit-<id>` — 이전 unit 의 대화 문맥을 잇지 않고 worktree 의 실제 코드만 잇는다; 결과 `worker-result.json`, `DOC_GAP`/`USER_DECISION` 처리는 전체 워커와 같다) → **targeted test**(`targeted_test` 를 저장소 루트에서 실행, `targeted-test-NN.log`) → `done.json`(version·unit_id·spec_hash·worker/targeted_test 상태·completed_at, 임시 파일 + `mv`). `run_worker` 의 장치(워커 규칙·[REFERENCE CODE]·스키마·index 지문·기준선 가드·before/after tree·manifest 불변·write-set 검사·DONE/UNDECIDED 모순 검사)는 unit 호출에 그대로 쓰이고, 전체 범위 검사 뒤에 **같은 함수로 unit scope 검사**를 한 번 더 한다(`UNIT_SCOPE_VIOLATION`, 원복 없음). unit 사이에 리뷰어·수정자·검증자를 부르지 않는다.
- **unit 간 rolling context.** fresh 세션은 유지하되, 앞 unit 이 **실제 코드로 확정한** 구현 문맥만 `implementation-context.json`(`{version, completed_units, facts[{kind, subject, note, source_unit}]}`, kind 는 `CONTRACT_BINDING`·`REUSE`·`ENTRY_POINT`·`INVARIANT` 넷뿐)으로 압축해 다음 unit 워커·test-fix 프롬프트의 `[IMPLEMENTATION CONTEXT]` 블록에 넣는다. 별도 요약 모델·stage·합의·리뷰는 없다 — 각 unit 워커(및 test-fix)가 결과 JSON 의 `context_updates{upsert,remove}` 로 후보를 내고 러너가 `(kind, subject)` 키로 기계적으로 fold 한다(같은 키 upsert 는 제자리 교체, remove 는 삭제; 의미 병합 없음). 확정은 targeted test **PASS 뒤**에만: 워커 → fix 순서의 update 를 `units/<id>/context-updates.json` 에 보존하고 `done.json` 을 쓴 뒤 lock 순서대로 유효한 done 체크포인트의 update 를 다시 fold 해 파일을 재구성한다(파생 상태 — 실패한 unit 의 update 는 pending 으로 버려지고, spec_hash 로 무효화된 체크포인트의 update 는 재사용하지 않으며, 같은 unit 재처리로 중복 append 되지 않는다). 규범(무엇을 해야 하는가)은 합의 문서 > 현재 코드 > 이 파일, 현재 상태(무엇이 존재하는가)는 현재 코드 기준이다 — 앞 unit 의 코드가 문서와 충돌하면 그 코드를 precedent 로 따르지 않고 scope 밖이면 DOC_GAP 으로 보고한다. 워커는 적힌 symbol 의 현재 구현을 확인·재사용하되 코드 탐색을 생략하지 않는다. hard size limit 은 두지 않는다 — 중복 키 금지·문서 복제 금지·obsolete 제거로 수렴시킨다.
- **targeted test 는 리뷰의 대체물이 아니다.** 다음 unit 이 깨진 코드 위에 쌓이는 것을 막는 장치일 뿐이다. 실패하면 unit 범위 안에서만 수정(`prompts/worker-unit-fix.md`, 워커 역할, 이후 unit 기능 선행 구현 금지)하고 바로 재테스트한다 — 리뷰어를 부르지 않는다. 수정 횟수는 `MAX_TEST_RETRIES` 를 재사용하며 소진하면 `UNIT_TEST_RETRIES_EXHAUSTED`.
- **checkpoint / resume.** `run-state.json` 은 힌트다. 재실행은 lock 검증 → 앞에서부터 `units/<id>/done.json` 의 내용과 현재 lock 의 unit spec 지문(`spec_hash`)을 대조 → 첫 미완료 unit 부터 재개한다(01/02 완료 후 03 에서 멈췄으면 01/02 워커를 다시 부르지 않는다). 중간에 멈춘 unit 은 워커부터 다시 돌되 `before.tree` 는 첫 시도의 것을 재사용한다(unit 시작 시점의 증거). manifest 를 바꾸면 impl PASS 가 무효라 재합의를 거치고, 워커 진입에서 lock 과 다르면 멈춘다 — 사용자가 lock 을 지우면 spec 이 그대로인 unit 의 체크포인트만 유지된다. 단 **직렬 의존성**: 어떤 unit N 을 다시 실행해야 하는데 N 뒤에 완료 체크포인트가 있는 unit 이 있으면 `UNIT_CHECKPOINT_CHAIN_STALE` 로 멈춘다(뒤 unit 의 spec 이 그대로여도 재사용하지 않고, 자동 원복·replay 도 하지 않는다). 어느 체크포인트도 최종 품질 승인이 아니다.
- **기존 전체 review / verify 는 그대로다.** 모든 unit 완료 후 unit 별 `worker-result.json` 을 합쳐 `.agent-work/worker-result.json` 으로 두고 기존 `impl-review-loop.sh`(워커 진입 기준선 대비 전체 feature diff) → verify(`TEST_CMD`/`LINT_CMD`) 를 현재와 동일하게 수행한다. 컨벤션·설계 일치 판정은 전부 이 전체 review 의 책임이며, unit 분할은 그 책임을 줄이지 않는다.

이 정책의 회귀는 `tests/smoke-implementation-units.sh`(LLM 호출 없음, mock claude/fake codex): 01→02→03 직렬·겹침 없음 / Unit 01 실패 시 02 미호출 / 03 중단 후 재실행은 03 부터 / spec_hash 불일치 체크포인트 무효 / lock≠원본·호출 중 변경 → `UNITS_MANIFEST_CHANGED` / unit scope 밖 → `UNIT_SCOPE_VIOLATION`(원복 없음) / unit 사이 리뷰어·수정자 호출 0회 / targeted test 실패 → fix → 재테스트 · 재시도 소진 / 모든 unit 뒤 final review 1회 → verify → DONE / manifest 변경 시 impl PASS 무효 / 스키마·부분집합 검사 / claude 워커도 unit 마다 fresh 세션 / rolling context(01 fact → 02 프롬프트, 실패 unit 미확정, fix 정정 반영, 같은 키 replace, remove 미전달, 재개 시 전달, 무효 체크포인트 미재사용, 추가 모델 호출 0회) / 앞 unit 무효화 + 뒤 unit 완료 → `UNIT_CHECKPOINT_CHAIN_STALE`(워커 0회, 원복 없음).

## Phase 2 — 보고 + finalize 질문 (오케스트레이터)

`DONE`이면 변경 요약·라운드 수(`run-state.json.history`, `usage.jsonl`)·`decisions.md` 주요 결정·`delegated_choices`를 한 번에 보고한다. 실행 중 워커 `DOC_GAP`, 리뷰어 `CONTRACT_VIOLATION`/`UNDECIDED_APPROACH`, 반복된 수정자 수정이 있었으면 그 지점의 implementation.md/approach.md 가 material decision 을 충분히 정했는지(어떤 material 선택이 워커에게 남았는지, 반대로 local expression 을 불필요하게 REQUIRED 로 적었는지)를 함께 분석해 보고한다 — 모델 이름별 문서 길이 조정·capability score·profile 은 만들지 않는다. `DONE` 은 리뷰 승인 + 전체 `TEST_CMD`/`LINT_CMD` 통과 + 승인 지문 유효를 뜻하며 여기서 상태 기계는 끝난다 — 러너는 worktree 를 지우거나 원본에 반영하지 않는다.

보고 뒤 **사용자에게 finalize 여부를 묻는다**(자동 실행 금지):

> 작업이 완료되었습니다. 피처 worktree 결과를 원래 작업공간에 커밋 없이 반영하고 worktree 를 정리할까요?

- **승인** → `--finalize` 를 실행한다. 러너는 기존 worktree 만 찾고(없으면 만들지 않음) 검증(같은 저장소·브랜치 일치·러너 없음·`DONE`·승인 지문·기준선 B 존재·dirty submodule 없음) → archive → 원본에 무커밋 3-way 반영 → worktree/피처 브랜치 정리 순으로 진행하고, 결과를 보고한다. 종료 코드 0 = `FINALIZED`(또는 already finalized), 2 = `FINALIZE_CONFLICT` / `APPLIED_CLEANUP_INCOMPLETE`(사용자 확인 필요), 1 = 거부·오류(원본·worktree 불변).
  ```bash
  bash <skill_dir>/scripts/feature-run.sh --feature <id> --finalize     # 원본 working tree 에서 실행 (수동 --worktree/--branch 를 썼다면 같은 인자)
  ```
  반영 모델은 `HEAD` 대비 diff 가 아니다. worktree 생성 시 원본의 dirty 상태까지 snapshot 했으므로 `B` = 생성 당시 tree(`feature.json.bootstrap_tree`), `F` = 지금 worktree tree, `O` = 지금 원본 tree 로 두고 **`merge(B, O, F)`** 를 `git merge-tree --write-tree --merge-base=B O F` 로 object 상에서만 계산한다 — B 에 있던 원본 dirty 변경은 중복 적용되지 않고, 피처 실행 중 원본에서 생긴 변경(O)은 보존되며, 같은 파일의 떨어진 hunk 는 자동 병합된다. 결과는 원본에 **working tree 변경으로만** 들어간다: commit·stash·branch 변경·checkout·reset 없음, 실제 index 는 읽지도 쓰지도 않으므로 staged 상태가 byte 그대로 남는다(임시 index 로 `read-tree O` → `read-tree -m -u O R`). 적용 뒤 원본을 다시 snapshot 해 계산해 둔 merge tree 와 같은지 검증하고, 그 뒤에만 `git worktree remove` + `git branch -D`(정확히 피처 브랜치이고 다른 worktree 가 쓰지 않을 때) 를 한다. 결과 상태: 원래 브랜치 + 피처 코드가 working tree 에 반영 + 커밋 없음 + worktree/브랜치 제거. **여기서 피처 작업은 끝이다.** 커밋은 사용자가 따로 요청할 때만(강제 규칙).
  - archive: 반영·삭제보다 먼저 `<원본>/.agent-work/archive/worktree/<id>/<timestamp>/` 에 `manifest.json`(feature.json + B/O/F/merge tree), `feature.patch`(B→F, `--binary`), `finalize.json`(status·trees·`source_after_tree`·cleanup·충돌 목록), `agent-work/`(worktree 의 `.agent-work` 사본)를 남긴다. archive 실패 = finalize 중단(아무것도 바꾸지 않음).
  - `FINALIZE_CONFLICT`(exit 2): B/O/F 가 같은 부분을 바꿨다. 자동 해결·모델 위임 없음. 원본 내용·index·worktree·브랜치·archive 전부 그대로이고 충돌 경로는 로그와 `finalize.json.conflict_files` 에 있다. 사용자가 원본 쪽을 정리하거나 worktree 쪽을 고친 뒤(worktree 를 고쳤으면 러너 재실행으로 재승인·verify) 같은 명령으로 재시도한다.
  - `APPLIED_CLEANUP_INCOMPLETE`(exit 2): 원본 반영과 검증은 끝났는데 worktree 제거나 브랜치 삭제가 실패했다. 반영은 되돌리지 않는다. 사유(`finalize.json.cleanup.error`)를 사용자에게 보고하고, 해소 뒤 같은 명령을 다시 실행하면 정리만 재시도한다(delta 재적용 없음).
  - 재실행 안전: 같은 lifecycle 의 `FINALIZED` 기록이 있으면 `already finalized` 로 끝나고(worktree 재생성·delta 재적용 없음), finalize 이후 원본이 바뀌었으면 `FINALIZE_STALE` 로 알린다. `bootstrap_tree` 가 없는 오래된 worktree(version 1 의 `new-from-branch`)는 기준선을 추측하지 않고 거부한다 — 그 결과는 사람이 옮긴다.
- **거부·보류** → worktree·피처 브랜치·원본 모두 그대로 두고 종료한다. 사용자에게 worktree 경로와 브랜치만 다시 알려 준다.

## 강제 규칙 (어길 수 없음)

- **검증자는 게이트지 설계자가 아니다.** REVISE_DOC은 여섯 가지 입장 조건(요구·결정·계약 위반 / 근거: 문서 대조 DIRECT_MISMATCH 또는 실행 경로 REACHABLE_FAILURE / 명시 계약과 다른 결과·권한·비밀·영속 데이터·구현 불가 영향 / 이번 변경이 만들거나 활성화 / 지금 결정 없이는 진행 불가 / 정확한 근거 위치)을 모두 만족할 때만, ASK_USER는 별도 네 조건(어디에도 미결정 / 동작·데이터·보안·범위가 갈림 / 기존 계약·패턴이 확정 못 함 / 없이는 시작 불가)을 만족할 때 등록된다. 단, 이번 피처가 직접 만들거나 활성화하는 blocker가 정확히 입증되고 확정 요구·사용자 결정·범위를 함께 지킬 안전한 구현이 없을 때는 ASK_USER 1·3조건의 예외로, 충돌이 입증된 계약에 한해서만 사용자 결정을 다시 요구한다. 범위 안의 안전한 대안이 있거나 기존 결함만 있는 경우에는 적용하지 않는다. 스키마와 러너가 근거 필드, 사용하지 않는 필드의 공백, id 유일성, Round 2 `origin`의 형식과 참조 대상 존재(직전 이슈 id, docs diff에서 실제 바뀐 파일)를 강제하며 어긋나면 검증자 응답 오류로 중단한다. 수정과 신규 blocker 사이의 의미적 인과관계까지 러너가 보장하지는 않는다 — 그것은 `tests/validator-cases.md` 감도 회귀 세트의 몫이다. 순수 정책 미결정은 `POLICY_UNDECIDED` + `UNDECIDED_CHOICE`로 표현해 충돌 계약이나 실패 경로를 지어내지 않게 한다. 검증자 프롬프트는 두 층이다 — 공통 계약(`prompts/validator-review-design.md`/`-impl.md`: 관할·탐색 범위·입장 조건·출력 형식, 모델과 무관)과 판정 전략 오버레이(`prompts/validator-overlays/<프로필>.md`, `[VALIDATOR PROFILE: …]` 블록으로 task prompt 끝에 붙음). 프로필은 `config.sh`의 `VALIDATOR_PROFILE`(compact / guided / conservative / none)이며 비워 두면 `validator_profile` 헬퍼가 `VALIDATOR_MODEL`로 기본값을 고른다(sol→compact, astra→guided, 그 외→conservative). 오버레이는 계약을 바꾸지 못하고 "그 계약을 어떤 순서·깊이로 판정할지"만 담는다 — 모델별로 계약 파일을 복제하지 않는다. 프로필 이름이 있는데 파일이 없으면 검증자를 부르지 않고 실패한다. 검증자 프롬프트(공통 계약·오버레이 모두)·스키마·러너 검사 중 하나라도 바뀌면 `config.sh`의 `VALIDATOR_CONTRACT_VERSION`을 올린다. 러너가 그 값과 다른 이전 PASS를 자동 무효화하므로 `--new` 없이 재실행하면 된다. 검증자는 최소 불변식만 요구하고 해결 방법을 처방하지 않는다. 디자이너는 5단계 판정을 거쳐 REJECT하고, ACCEPT해도 검증자의 처방을 복사하지 않는다. Round 1은 전부, Round 2부터는 직전 이슈 종결 검토와 직접 회귀만. 파이프라인 운영(git 기준선·지문·테스트 순서)은 러너 책임이며 문서 blocking 사유가 아니다.
- **리뷰어는 병합 게이트지 개선자가 아니다.** issue 는 여섯 가지 입장 조건(이번 diff 가 만든 문제 / 아홉 category 중 하나: CONTRACT_VIOLATION·UNDECLARED_BEHAVIOR·REACHABLE_BUG·SECURITY_OR_DATA_RISK·REDUNDANT_CONTROL_FLOW·REDUNDANT_CODE·TEST_CONTRACT_GAP·OUT_OF_SCOPE_CHANGE·UNDECIDED_APPROACH / 증거: DIRECT_MISMATCH·REACHABLE_FAILURE·SEMANTIC_REDUNDANCY / verify 전에 반드시 해결(UNDECIDED_APPROACH 는 동작이 맞아도 예외) / 기존 결함·장래 개선이 아님 / 정확한 위치)을 모두 만족할 때만 등록된다. 명명·포맷·선호 리팩터링·정상 대응 분기·`delegated_choices` 보고 누락·합의된 동작의 추가 black-box 테스트는 issue 가 아니다. `required_outcome` 은 결과만 적고 기법을 처방하지 않는다. action 은 `FIX_CODE`(수정자) / `DOC_GAP`(사용자 결정 — 루프 exit 3 → 러너 `NEED_USER/REVIEW_DOC_GAP`) 둘뿐이다. DOC_GAP 에는 `user_question`(비어 있지 않음)·`options`(≥2, 실제로 갈리는 solution shape 만, 우열 없음)가 필수이고 FIX_CODE 는 둘 다 빈 값이다(스키마 + 루프 검사). DOC_GAP 은 impl 재합의(검증자·디자이너)로 가지 않는다 — 사용자가 고른 순간 그 gap 의 설계 판단은 종결이며 review-gap 워커가 그대로 구현하고 다음 리뷰가 검증한다. 같은 리뷰의 FIX_CODE 는 그 워커가 함께 처리하므로 DOC_GAP 이 하나라도 있으면 수정자를 먼저 부르지 않는다. 리뷰 diff 는 러너가 워커 진입 직전에 기록한 `worker-baseline.tree` 대비다(피처 이전 미커밋 변경은 이번 작업이 아니다). `OUT_OF_SCOPE_CHANGE` 는 수정자에게 가지 않는다 — 러너가 수정자 호출 전에 `FOREIGN_WORKTREE_CHANGE` 로 사용자에게 돌려보내며, 어떤 역할도 범위 밖 파일을 원복하지 않는다(`pre_bash_guard` 가 `git restore`/`checkout --`/`reset --hard` 를 차단). 워커·수정자의 git index 조작(add/reset/stash/restore --staged)은 금지이며, 러너·루프가 호출 전후 index 지문을 비교해 바뀌었으면 자동 복구 없이 중단한다. 루프가 증거·action 별 필드, id 유일성, Round 2 `origin`(UNRESOLVED_PREVIOUS / FIX_REGRESSION / NEWLY_EXPOSED_BY_FIX)과 참조 대상(직전 이슈 id, 수정 diff 에 실제로 바뀐 파일)을 강제하고 어긋나면 응답 오류로 중단한다. Round 1 은 전부, Round 2 부터는 직전 이슈 종결 검토와 수정이 만든 직접 회귀만. 같은 이슈가 내용 변화 없이 반복되면 `DEADLOCK`. 수정자는 `FIX_CODE` 의 required_outcome 만 구현하고 잘못된 이슈는 `decisions.md` 에 `[fix round N] <id> REJECT` 로 남긴다. 리뷰어 프롬프트·스키마·루프 검사 중 하나라도 바뀌면 `config.sh`의 `REVIEWER_CONTRACT_VERSION`을 올리고 `tests/reviewer-cases.md` 감도 회귀를 돌린다 — 유료 실행이므로 사용자 승인 후 `touch .claude/ALLOW_REAL_LLM_REGRESSION`(1회용)이 있어야 스크립트가 돈다. 오케스트레이터가 지시 없이 만들지 않는다.
- **막히면 AI끼리 풀지 말고 사용자에게 묻는다.** 러너가 자동으로 도는 루프는 성공 조건이 기계적인 두 가지뿐 — (리뷰 이슈 → 수정자 → 재리뷰), (테스트 실패 → 워커 1회 수정 → 재리뷰 → 재테스트). unit 단계의 (targeted test 실패 → unit 범위 수정 → 재테스트)는 두 번째 형태와 같고 같은 한도를 쓴다. 교착·라운드 초과·`UNDECIDED`·재시도 소진은 전부 즉시 사용자 반환이며, 러너·오케스트레이터 어느 쪽도 "다른 에이전트에게 다시 물어보는" 자동 복구를 추가하지 않는다.
- **테스트는 동작 계약 검증용이다** — 작성 순서는 강제하지 않는다. 워커는 `implementation.md`가 명시한 동작 계약을 검증하는 테스트만 쓰고, 테스트 편의만을 위한 운영 API·분기·추상화·가시성 변경과 커버리지 수치 목적의 테스트는 금지. 리뷰어는 명시 요구 테스트의 누락, 내부 호출·private 상태만 검증하는 테스트, 테스트 편의용 운영 코드 변경을 `TEST_CONTRACT_GAP` 으로 올린다. 이미 합의된 외부 동작을 검증하는 추가 black-box 테스트는 문서에 이름이 없어도 issue 가 아니다.
- **합의 문서는 코드 diff 를 사전에 고정하지 않는다 — material implementation contract 를 고정한다.** `implementation.md`+`approach.md` 가 material decision(외부 동작·API 계약, public/package 계약, 영속 데이터, transaction/lock/concurrency, 보안 경계, 책임 배치, REUSE/EXTEND vs 새 병렬 책임, sync/async, retry/fallback/cache/error semantics, 외부 호출 topology·횟수, 의미 있는 비용 특성, 새 production 구조물, 사용자·convention 이 직접 요구한 방식)을 결정하고 검증자가 합의한다(검증자 `CODE_SPEC_GAP` = material 구현 계약 하나가 열려 있음, 일곱 입장 조건 + "이 선택을 워커에게 맡기면 제품/아키텍처/책임 경계/상태 의미/I/O 비용/안전성 중 무엇이 달라지는가" gate — helper/local naming/intermediate/if·switch/for·stream/동등 overload/bounded local collection 표현은 근거가 아니다). 워커는 그 계약 안에서 convention → material contract → 직접 범위의 기존 표현 → 관용 표현 → 가장 단순한 구현 순으로 local implementation expression 을 직접 고르되, 문서가 요구하지 않은 standalone production class·interface·repository·service·converter·shared helper·새 persistence/query path·새 state/result/context abstraction 은 만들지 않는다(local autonomy 는 확대, architectural surface area autonomy 는 확대하지 않음). 워커·수정자가 material REQUIRED 와 다른 기법·책임 위치·호출 횟수·상태 순서를 쓰거나 REUSE/EXTEND 로 지정된 symbol 옆에 같은 책임의 병렬 구현을 만들면 **동작이 같아도** 리뷰어가 `CONTRACT_VIOLATION` 으로 잡고, 단순 직접 구현으로 완전히 대체 가능한 새 standalone abstraction 은 `REDUNDANT_CODE` 로 잡는다. 반대로 helper/local naming/intermediate/if·switch/for·stream/동등 overload/bounded collection 표현/반환 직전 alias 의 차이는 approach.md 가 REQUIRED 로 적어 두었더라도 issue 가 아니다(명시 convention·사용자 결정이 요구한 경우만 예외) — 문서에 적혀 있다는 사실만으로 모든 문장이 동등한 강도의 contract 가 되는 것은 아니다. 리뷰어의 근거는 문서·project convention·인용된 reference 뿐이며 문서가 지정하지 않은 재사용 후보를 찾지 않는다. 워커가 material decision(책임 위치, shared component 확장 vs 병렬 책임, 호출 횟수가 달라지는 접근, transaction/lock/cache/retry, 외부 동작이 달라지는 분기, 새 standalone abstraction 필요 여부)을 문서·reference·convention·직접 범위 precedent 어디서도 찾지 못하면 `DOC_GAP` 으로 돌려보내고, 골라 버렸으면 리뷰어가 `UNDECIDED_APPROACH` + `DOC_GAP` 으로 잡는다 — 어느 쪽이 나은지는 판단하지 않는다. local expression 으로는 DOC_GAP 을 만들지 않는다. 합의의 역할 경계: design consensus = 구현 전 요구·설계 계약 확정, impl consensus = **최초 워커 진입 전** implementation/approach/units 의 실행 가능성 검증(사전 게이트), 워커·리뷰어 DOC_GAP = 구현 중 발견된 미결정 material 사항 → 사용자에게 직접 escalation → 사용자 결정이 최종 → child validator/designer 재승인 없음. 리뷰어·워커의 구체적 질문에 답해 approach 를 보강한 것은 새 implementation proposal 이 아니라 pending gap 의 resolution 이다.
- 모호한 요구·갈리는 설계 판단은 추측 금지 — 사용자 질문 후 문서 반영, `decisions.md`에 `- [USER-QUESTION][scope=design|impl] <질문> → <답>` 기록. scope 는 "그 질문이 어느 합의 gate 에서 발생했는가"다: Phase 0 질문·design ASK_USER/DEADLOCK/MAX_ROUNDS → `scope=design`, impl ASK_USER/DEADLOCK/MAX_ROUNDS·워커/리뷰어 DOC_GAP·USER_DECISION → `scope=impl`. 구현 후 gap 의 답은 어느 pending gap 에 대한 답인지 기계적으로 확인되도록 세 번째 태그를 붙인다 — `[USER-QUESTION][scope=impl][review-issue=<issue id>]`(리뷰어) / `[USER-QUESTION][scope=impl][worker-gap=<unit id 또는 review-gap>#<n>]`(워커). 모든 pending gap 에 비어 있지 않은 답이 있어야 워커가 재개되며, 기존 `[scope=impl]` 의미(impl 지문 포함, design PASS 무영향)는 그대로다. 후기 단계의 답 때문에 `design.md` 를 고쳐야 해도 scope 를 design 으로 바꾸지 않는다 — `design.md` 변경 자체가 design 재합의를 일으킨다.
- 판정은 스키마 검증된 JSON만 신뢰한다: 검증자(`PASS/BLOCK`), 리뷰어(`APPROVE/REQUEST_CHANGES`), 워커(`DONE/UNDECIDED` + `context_updates`, `schemas/worker-result.schema.json`). 모순 응답은 스크립트가 즉시 거부. "대충 통과 간주" 금지.
- 하위 실행은 반드시 `--model`/`-m` 명시(`config.sh` 한 곳에서 관리). 역할별 CLI 는 고정이 아니라 모델 ID 로 라우팅한다(`claude*` → claude, `gpt-*`/`o*`/`codex*` → codex, 그 외는 `<ROLE>_CLI` 명시). 검증자·리뷰어는 `run_readonly_json_role`(읽기 전용 + 스키마 JSON), 디자이너·수정자·워커는 `run_edit_role`(편집)로 호출되며 두 CLI 의 플래그 차이는 이 헬퍼 안에서만 다룬다. `core_rules.md`는 워커에게만, 선택 `conventions.md`는 전 역할에 이 헬퍼가 명시 주입한다(claude 호출은 `FEATURE_ROLE_CHILD=1` 을 달아 프로젝트 `inject_conventions.sh` 훅이 중복 주입하지 않게 한다; 훅은 interactive 오케스트레이터 세션당 첫 프롬프트에만 넣는다). Claude 세션은 stage/attempt 단위(`designer-<design|impl>`, `validator-<design|impl>`, `reviewer-aNN`, `fixer-aNN`, `worker-unit-<id>`)로만 `--resume` 하고 그 밖으로 대화 문맥을 넘기지 않는다 — 상태는 문서·JSON·체크포인트·지문으로만 전달. 워커에는 추가로 `config.sh`의 `WORKER_SKILLS`(기본 비어 있음; 탐색 순서 `.claude/skills/<이름>/SKILL.md` → `.agents/skills/<이름>/SKILL.md`)의 본문을 `[WORKER SKILL]` 블록으로 붙일 수 있다. 목록에 있는데 어디에도 없으면 워커를 실행하지 않고 실패한다. 프로젝트 codex hooks(`.codex/hooks.json` + `worker_guard.sh`)는 매 툴 호출에 별도 적용.
- **워커와 리뷰어·수정자는 파일 삭제 절대 금지** — 어느 CLI 로 돌아도 훅이 강제한다(claude 쪽 `pre_bash_guard`, codex 쪽 `worker_guard`). 러너의 `--new` 아카이브도 `mv`만 쓴다. 삭제가 필요하면 `decisions.md`에 대상·사유를 남기고 사용자 에스컬레이션.
- 워커·리뷰어·수정자는 커밋·푸시 금지. 커밋은 사용자가 요청했을 때만 — **finalize 와 commit 은 별개다.** 두 상태를 구분한다: ① worktree 가 아직 있는 `DONE` — 오케스트레이터가 그 worktree 에서 `verify_approved_fingerprint`(config.sh)로 승인 지문을 재확인한 뒤 `touch .claude/ALLOW_COMMIT`(1회용 플래그) 후 `fixer` 세션에 별도 호출로 위임. ② `FINALIZED`(worktree 는 없고 결과가 원본 working tree 에 있음) — 승인 지문은 worktree 와 함께 사라졌으므로 대신 원본에서 `feature_finalized_source_current <id>`(feature-worktree.sh; archive `finalize.json.source_after_tree` 와 지금 원본 tree 대조)가 성공해야만 커밋을 허용한다. finalize 이후 사용자가 원본을 고쳤으면(`FINALIZE_STALE`) 승인된 상태 그대로가 아니므로 그 변경을 사용자에게 확인시킨 뒤 결정한다. 어느 경우든 커밋은 원본 working tree 에서, 사용자 지시 뒤에만.
  ```bash
  bash -c 'source <skill_dir>/config.sh; source <skill_dir>/scripts/feature-worktree.sh; feature_finalized_source_current <id>'
  ```
- **finalize 는 사용자 승인 없이는 실행하지 않는다.** `DONE` 뒤 오케스트레이터가 반드시 묻고, 승인 답이 있을 때만 `--feature <id> --finalize` 를 실행한다. 러너·훅·다른 에이전트가 자동으로 부르지 않는다.
- **finalize 의 불변식.** 3-way(B/O/F) 충돌은 자동 해결하지 않는다(모델 위임 금지, `FINALIZE_CONFLICT` 로 반환). 원본 index 는 읽지도 쓰지도 않는다(임시 index 만). 원본에 commit·stash·checkout·reset 을 하지 않는다. archive 가 만들어지기 전에는 어떤 파괴적 정리도 하지 않고, finalize 가 실패하면 worktree·브랜치를 삭제하지 않는다. 적용 결과가 기대 merge tree 와 다르면 실패로 보고만 하고 자동 원복하지 않는다(사용자 변경을 추측해 지우지 않는다 — archive 의 patch/tree 로 사람이 복구).
- 마지막 APPROVE 이후 코드가 조금이라도 바뀌면 재리뷰 없이 종료 금지 — 러너의 verify 단계가 지문으로 강제한다.
- 모든 하위 실행은 stdin을 닫고 돌린다(스크립트 시작부 `exec </dev/null`). 러너를 다른 명령·heredoc과 한 줄로 묶지 않는다.
- **진행 확인은 "프로세스 생존"이 아니라 "실제 진척"으로 판정** — `live.log` 최근 갱신과 CPU 시간 증가를 본다. 둘 다 멈춰 있으면 입력 대기·행(hang)이다: 해당 PID만 TERM으로 정리하고(`pkill` 광역 금지) 원인 확인 후 같은 명령으로 재실행하면 러너가 재개 지점을 찾는다. 중단된 라운드 산출물은 archive로 옮긴다.

## 공유 working tree 와 변경 소유권

`worker-baseline.tree` 는 시점 기준선이지 변경 소유권 증거가 아니다. git 은 같은 working tree 에서 생긴 변경이 워커의 것인지 다른 채팅 세션의 것인지 기록하지 않는다. 그래서:

- 같은 working tree 에서 피처 실행 중 다른 writer 의 변경이 존재할 수 있으므로, **범위 밖 변경은 자동 원복하지 않는다.** 현재 내용을 보존하고 `FOREIGN_WORKTREE_CHANGE`(리뷰어 판정) 또는 `SCOPE_VIOLATION`(write-set 대조) 으로 중단한다. 되돌릴지 보존할지는 사용자가 정한다.
- 이번 피처의 변경은 시점이 아니라 **범위**(`feature-scope.json` → 워커 진입 시 `feature-scope.lock.json` 으로 확정)로 정의한다. 리뷰 diff 와 승인 지문은 범위 경로만 본다(`new_file_roots` 아래는 기준선에 없던 신규 파일만). manifest 는 검사 기준이면서 에이전트가 쓸 수 있는 `.agent-work` 안에 있으므로, 호출 전후 원본·lock 해시를 대조해 바뀌었으면 `SCOPE_MANIFEST_CHANGED` 로 중단한다. 같은 이유로 `worker-baseline.tree` 도 호출 전에 읽은 값으로만 소유권을 판정하고, 호출 중 바뀌었으면 `SCOPE_BASELINE_CHANGED` 로 중단한다. 범위 안 파일을 다른 세션이 동시에 고치는 경우는 구분할 수 없다 — 그 파일의 변경은 이번 작업으로 리뷰된다.
- **모든 피처는 처음부터 피처별 전용 git worktree 에서 돈다** (`feature-run.sh --feature <id>`, Phase 0). 같은 프로젝트의 여러 피처를 동시에 실행해도 서로의 `.agent-work`·문서·리뷰·소스 변경이 섞이지 않고, 원본 working tree 에도 보이지 않는다. 부트스트랩(`scripts/feature-worktree.sh`)은 원본의 지문 → `snapshot_worktree_tree` → 지문 재확인으로 일관된 snapshot 만 쓰고(다르면 worktree 를 만들지 않고 실패), `git worktree add --no-checkout` + 임시 index 의 `read-tree`/`checkout-index` 로 materialize 한 뒤 worktree 에서 다시 snapshot 해 같은 tree 인지 검증한다. worktree 의 index 는 HEAD 이므로 원본의 미커밋 변경은 unstaged 로 보인다. 원본에서 러너가 실행 중이거나(`.agent-work/.runner.lock/pid` 생존) dirty submodule 이 있으면 거부한다. 러너는 진입 시 `.agent-work/.runner.lock` 을 `mkdir` + pid 기록 한 단위로 원자적으로 잡아 같은 트리에 두 러너가 들어오지 못하게 하고, 종료 시 푼다. pid 가 있고 죽은 stale 락만 회수하며 pid 가 아직 없는 락은 초기화 중으로 보고 훔치지 않는다(그런 락이 확실히 죽은 것이면 사용자가 직접 지운다). gitignore 된 `.codex/`·`.claude/settings.json`·`.claude/hooks/` 는 worktree 에 없으면 원본에서 복사해 훅 게이트를 유지한다(복사 실패는 부트스트랩 실패). worktree 로 들어간 뒤 `PROJECT_ROOT`·`CORE_RULES_FILE`·`CONVENTIONS_FILE` 은 그 worktree 로 재바인딩되고 하위 루프에도 `FEATURE_PROJECT_ROOT` 로 상속된다 — 규칙·conventions·프로젝트 로컬 워커 스킬을 원본이 아니라 snapshot 시점의 사본에서 읽는다(실행 엔진 위치 `SKILL_DIR` 는 그대로). 피처 worktree 밖의 파일은 워커·수정자·리뷰·승인 대상이 아니며, 다른 세션은 원래 디렉터리에서 계속 작업한다. 완료 후 merge·commit·rebase·worktree 삭제는 자동으로 하지 않는다 — 사용자에게 branch/worktree 결과를 보고하고 finalize 여부를 묻는다. 유일한 예외는 **사용자 승인에 따른 명시적 finalize 명령**(`--feature <id> --finalize`, Phase 2)이며, 그때도 원본에는 working tree 변경만 들어가고 커밋은 별도 요청이 있어야 한다. 부트스트랩은 finalize 의 기준선 B 를 `feature.json.bootstrap_tree`(version 2) 로 영구 기록한다 — 신규 snapshot 경로는 그 snapshot tree, 기존 브랜치 체크아웃(`new-from-branch`)은 생성 직후 worktree 의 snapshot 이다. 수동 `--worktree <디렉터리> --branch <이름>` 도 그대로 동작한다.

권장 구성: `--feature <id>` 전용 worktree + `feature-scope.json` 필수 + write-set 검사 + 범위 밖 변경 자동 원복 금지 + main 자동 반영 금지. `--feature` 없이 공유 worktree 에서 돌리는 것은 호환용이며, 그때는 앞의 원복 금지·범위 한정이 최소 안전장치다. 부트스트랩·finalize 회귀는 `tests/smoke-feature-worktree.sh`(LLM 호출 없음): clean 생성 / dirty tracked·untracked·권한·symlink 동일 materialize / `.agent-work`·ignored 제외 / 원본 HEAD·branch·index·working tree 불변 / 피처 간·원본 간 격리 / snapshot 도중 원본 변경 시 실패 / 동일 피처 재실행 재사용 / 수동 `--worktree` 호환 / 러너 실행 중·dirty submodule 거부, 그리고 finalize(러너 대신 run-state `DONE` + 승인 지문을 파일로 재현): clean 원본 반영·커밋 없음·index 불변·worktree/브랜치 제거·archive / 재실행 already finalized·delta 중복 없음 / bootstrap 당시 dirty X 중복 적용 없음·untracked 신규 전달 / 원본 별도 변경·staged 상태 보존 / 같은 파일 비충돌 자동 병합 / 같은 hunk 충돌 → `FINALIZE_CONFLICT` 전부 보존 / binary·실행 권한·symlink / archive 실패 시 불변 / 브랜치 삭제 실패 → `APPLIED_CLEANUP_INCOMPLETE` 후 정리만 재시도 / 기준선 없는 이전 metadata 거부 / 러너 실행 중·DONE 아님·승인 stale·잘못된 cwd·검증 뒤 원본 변경 거부.

이 정책의 회귀는 저장소 루트의 `tests/smoke-foreign-change.sh` 다(실제 LLM 호출 없음, mock claude, 임시 저장소). 다섯 사례: ① 기준선 기록 후 워커 역할이 범위 안 파일을, 다른 세션 역할이 범위 밖 파일을 고친 상태에서 리뷰어가 `OUT_OF_SCOPE_CHANGE` 를 내면 exit 2 / `FOREIGN_WORKTREE_CHANGE` / 수정자 호출 0회 / 두 파일과 index 불변 / 리뷰어 diff 가 실제로 캡처됐고 범위 안 파일은 있고 범위 밖 파일은 없음 ② 수정자의 범위 밖 쓰기 → `SCOPE_VIOLATION`, 원복 없음 ③ 승인 지문 양방향 — 범위 밖 외부 변경은 승인 유지·재사용, 범위 안 내용·실행 권한·범위 정의 변경은 승인 무효 ④ 범위 밖 파일을 범위 안 경로로 rename 하면 출발지가 위반으로 잡힘(`--no-renames`) ⑤ manifest 가 있는데 잘못되면 전체 트리 지문으로 조용히 돌아가지 않고 실패 ⑥ manifest canonical 규칙과 roots-only 유효 ⑦ 기본 설정에서 워커 스킬 미주입 ⑧ 수정자가 manifest 를 넓혀도 `SCOPE_MANIFEST_CHANGED`, 원복·재호출 없음, lock≠원본이면 진행 불가 ⑨ `new_file_roots` 아래 기준선 파일 수정은 위반·신규 생성은 허용, 지문은 신규 엔트리만 ⑩ 이전 호출이 만든 root 파일의 후속 수정은 허용 ⑪ APPROVE 뒤 lock 은 그대로 두고 원본 manifest 만 바뀌면 승인 지문 실패(원본·lock 일치 검사가 `compute_approval_fingerprint` 안에 있다) ⑫ 피처가 만든 root 파일의 삭제·symlink 화(D/T)는 위반 ⑬ 수정자가 `worker-baseline.tree` 를 빈 tree 로 바꾸고 root 아래 기존 파일을 고치면 `SCOPE_BASELINE_CHANGED`, 파일·기준선 모두 자동 복구 없음, 복구 없이 재실행하면 모델 호출 0회로 다시 중단, 복구 후에만 재개 ⑭ 기준선과 manifest 를 함께 바꾸면 `SCOPE_MANIFEST_CHANGED` 로 먼저 멈추더라도 가드가 남아, manifest 만 고친 재실행은 `SCOPE_BASELINE_CHANGED` 로 모델 0회 재중단. `tests/install-smoke.sh` 8절은 필수 워커 스킬이 없으면 `run_worker` 가 실제로 중단하고 codex 를 부르지 않음, worker 단계 진입 시 원본≠lock 이면 `NEED_USER`/`SCOPE_MANIFEST_CHANGED` 가 실제로 기록되고 codex 를 부르지 않음, 11d 절은 verify 단계의 worker-fix 가 기준선과 범위 밖 파일을 바꿔 멈춘 뒤 테스트가 통과하도록 바뀐 재실행이 테스트·codex·리뷰어 호출 0회로 다시 멈추고 기준선 복구 후에만 DONE 에 이르는지 본다. 그리고 워커가 `worker-baseline.tree` 를 빈 tree 로 바꾸고 root 아래 기존 파일을 고치면 `SCOPE_BASELINE_CHANGED` 로 review 에 들어가지 않고 원복도 하지 않으며, 복구 없이 재실행하면 codex 호출 0회로 다시 멈추고 복구 후에만 워커가 재개됨을 본다. 리뷰 루프·수정자 프롬프트·범위 함수(`config.sh`)를 바꾸면 돌린다. 범위 지문은 `snapshot_worktree_tree` 의 tree 엔트리(모드·유형·blob·경로)와 manifest 자체를 해시하므로 내용뿐 아니라 실행 권한·symlink 목적지·생성/삭제까지 잡는다.

## 토큰 절약 구조 (스크립트에 내장)

- 오케스트레이터는 러너 호출 1회당 턴 1회만 소비한다. 러너 내부의 라운드 진행·재진입은 상위 세션 API 호출을 발생시키지 않는다.
- claude 로 라우팅된 역할은 역할별 세션 유지: `designer-doc`, `validator`, `worker`(전체 호출·verify 의 worker-fix), `reviewer`, `fixer`. 첫 호출이 `--session-id`, 이후 `--resume`. `reviewer`와 `fixer`는 절대 같은 세션으로 합치지 않는다. unit 호출은 예외다 — `worker-unit-<id>` 로 unit 마다 fresh 세션이며 이전 unit 의 문맥을 잇지 않는다(잇는 것은 worktree 의 코드뿐). codex 로 라우팅된 역할은 `codex exec` 가 무상태라 세션을 이어가지 않는다.
- 사용량은 `$WORK_DIR/usage.jsonl`에 CLI invocation 한 번당 행 1개(세션 누계 아님, `--resume` 해도 invocation 별). 필드: `role`/`cli`/`model`/`label`/`invocation_id`, `input_uncached`(cache 제외 입력)·`cache_read`·`cache_write`·`output`·`input_effective`(셋의 합, 진단용 파생값), `reasoning_output`(codex 만, output 의 부분집합 — total/cost 에 다시 더하지 않음), `num_turns`·`duration_ms`, `exit_code`/`success`. 비용은 provenance 로 나뉜다: `cost_usd` = provider 가 직접 보고한 실제 비용(claude `total_cost_usd`, codex 는 항상 `null`), `estimated_cost_usd` = codex 토큰 관측값 × 명시적 가격표(`config.sh` `codex_model_pricing`, 2026-09-23 공개 standard token rate, 현재 gpt-5.6·gpt-6 의 sol/luna 만 — 가격표에 없는 모델은 `null`), `cost_kind` = `reported|estimated|unknown`, `pricing_basis`. codex 추정은 `(input_tokens − cached_input_tokens) × input + cached × cached_rate + output × output_rate` 이며 실제 청구(월정액·long-context·특수 billing)가 아니라 모델/루프 비용 비교용이다. codex 행은 `codex exec --json` 이벤트 JSONL(`<raw>.events.jsonl`, stderr 는 `<raw>.stderr.log` 로 분리)의 `turn.completed.usage` 를 invocation 안에서 합산한다(input_total = uncached + cache_read + cache_write = `input_effective`, `tokens_total` = input_total + output). plain "tokens used" 텍스트는 읽지 않는다. telemetry 는 best effort — usage 이벤트가 없거나 깨지면 WARN 후 행을 생략하고 작업은 그대로 성공하며 같은 invocation 을 재실행하지 않는다. `cache_read` 는 invocation 안의 turn 누계일 수 있으니 `num_turns` 와 함께 읽는다. 집계는 `usage_summary`(config.sh) 로 별도 계산한다 — 전체와 `by_role`/`by_label`/`by_session` 마다 `invocations`·`reported_cost_usd`(= 옛 `cost_usd`, 의미 불변)·`estimated_cost_usd`·`combined_cost_usd_estimate`(reported + estimated, 추정치)·`cost_unknown_invocations`(둘 다 null)·`cache_read`·`num_turns`·`output`·`reasoning_output`·`cache_read_per_turn` 을 내며, legacy 행(`in`/`out`, v2 codex `tokens_total` 만 있는 행)도 읽는다. 임계치나 자동 판단은 두지 않는다. `usage.jsonl` 은 child invocation 만 담으므로 interactive 오케스트레이터 자체의 cache read 는 측정하지 못한다 — 변경 전후 비교는 상위 오케스트레이터는 CodeBurn, 하위 역할은 `usage_summary` 로 각각 보고, 세션 분리로 `cache_write`·`input_uncached` 가 늘 수 있으므로 성공 기준은 `cache_read` 단독 감소가 아니라 동일 피처 A/B 실행의 총비용·calls/turns·cache_read 를 함께 비교하는 것이다.
